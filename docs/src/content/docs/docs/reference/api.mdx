Toutes les routes sont servies par le serveur Bun, sur le port `PORT`.

## Correction

### `POST /v1/chat/completions`

Corps au format OpenAI (`model`, `messages`, `temperature`), plus un champ `correction_mode` utilisé pour la télémétrie. La réponse est un flux SSE :

```
data: {"delta":"Bonjour "}
data: {"delta":"à tous."}
data: {"done":true,"text":"Bonjour à tous.","duration":412}
```

En cas d'erreur pendant le flux : `data: {"error":"…"}`. Des lignes `: keepalive` sont émises toutes les cinq secondes.

### `/v1/*`

Les autres routes, dont `GET /v1/models`, sont relayées telles quelles au serveur du modèle.

### `POST /api/check`

Analyse le texte avec le [moteur de grammaire](/docs/decouvrir/moteur/) intégré (grammaria-rc). L'interface l'appelle en parallèle de la correction par le modèle.

```json
{ "text": "Les enfants était content." }
```

`text` est obligatoire, non vide, et limité à 20 000 caractères. Réponse (extrait) :

```json
{
  "matches": [
    {
      "offset": 12,
      "length": 5,
      "message": "Le verbe devrait être à la 3ᵉ personne du pluriel.",
      "shortMessage": "",
      "replacements": [{ "value": "étaient" }],
      "rule": {
        "id": "ACCORD_SUJET_VERBE",
        "issueType": "uncategorized",
        "category": { "id": "CAT_GRAMMAIRE", "name": "Grammaire" }
      }
    }
  ]
}
```

Les détections suivent le format JSON de LanguageTool, que le moteur reprend. Erreurs : 400 si le JSON ou le corps est invalide, 405 pour une autre méthode que `POST`, 503 si le correcteur échoue.

## Analyse et journal

### `POST /api/analyze`

Calcule le diff, le croise avec les détections, enregistre le résultat dans le journal, met à jour l'état des règles et renvoie le tout, avec ce qu'il faut afficher près du bouton Copier.

```json
{
  "original": "Ils on vu le film.",
  "corrected": "Ils ont vu le film.",
  "matches": []
}
```

`matches` est le tableau renvoyé par `POST /api/check`. Chaque faute indique sa `source` : `fiche`, `lt` (moteur de grammaire ; le nom vient de LanguageTool, dont le moteur reprend les règles) ou `accord` (déduit du diff), son `label` (nom fixe de la règle : titre de la fiche ou description de la règle du moteur) et son `message` (message du moteur, qui peut citer le texte). `original` et `corrected` sont limités à 20 000 caractères. Le journal n'enregistre ni le texte, ni la phrase, ni le mot, ni la correction, ni le message : seulement la règle, sa catégorie, la date et les compteurs.

Réponse :

```json
{
  "corrections": [
    {
      "start": 4,
      "end": 6,
      "avant": "on",
      "apres": "ont",
      "faults": [{ "ruleKey": "PAIRE:on/ont", "source": "fiche", "counted": true }],
      "fiche": { "titre": "on / ont", "astuce": "Remplacez par « avaient »…" }
    }
  ],
  "wordCount": 5,
  "faultCount": 1,
  "unclassifiedCount": 0,
  "score": 0,
  "week": { "texts": 12, "words": 840, "faults": 9, "score": 17.9 },
  "intervention": null,
  "reussites": [],
  "nouveauxBadges": []
}
```

`start` et `end` situent le passage dans le texte d'origine (fin exclue).

`intervention` vaut `null`, ou l'une des deux formes suivantes. Le serveur en choisit au plus une par texte et la compte dans le budget de la règle (une par règle et par jour).

```json
{
  "type": "astuce",
  "ruleKey": "PAIRE:on/ont",
  "titre": "on / ont",
  "texte": "Remplacez par « avaient »…"
}
```

```json
{
  "type": "choix",
  "choiceId": 57,
  "ruleKey": "PAIRE:on/ont",
  "titre": "on / ont",
  "explication": "Remplacez par « avaient »…",
  "avant": "Ils ",
  "apres": " vu le film.",
  "formes": [
    { "texte": "on", "correcte": false },
    { "texte": "ont", "correcte": true }
  ],
  "masque": { "start": 4, "end": 7 }
}
```

La réponse de `POST /api/analyze` porte aussi `tendance` : `null`, ou `{ ruleKey, titre, avant, depuis, motsParTaux }` quand l'une des règles fautives du texte revient moins souvent depuis sa première intervention (taux en fautes pour `motsParTaux` mots).

`masque` donne la position de la bonne forme dans le texte corrigé (fin exclue) : l'écran la masque tant que le choix attend une réponse. Le champ est absent quand la forme n'a pas pu être située.

`choiceId` identifie ce choix précis (c'est l'`id` de l'événement `choix` dans l'historique) : il est à renvoyer à `POST /api/rules/answer`. `avant` et `apres` sont l'extrait de la phrase de part et d'autre de la forme. `formes` est déjà dans l'ordre d'affichage, tiré au hasard par le serveur.

`reussites` liste les règles devenues « acquises » avec ce texte : `[{ "ruleKey": "PAIRE:on/ont", "titre": "on / ont" }]`.

`nouveauxBadges` liste les [badges](#badges) obtenus grâce à ce texte, dans l'ordre du catalogue : `[{ "id": "premier-texte", "titre": "Premier texte", "description": "Votre premier texte est corrigé : le journal de progression commence." }]`. Une erreur du calcul des badges ne fait jamais échouer l'analyse : la liste est alors vide.

## Cycle de vie des règles

L'état des règles est mis à jour à chaque `POST /api/analyze`. Les seuils sont définis dans `src/analysis/regles/seuils.ts`, la logique de transition dans `src/analysis/regles/cycle.ts`. Les dates sont en millisecondes depuis 1970.

### `GET /api/rules`

Toutes les règles suivies, de la plus récemment fautive à la plus ancienne.

```json
{
  "rules": [
    {
      "ruleKey": "PAIRE:on/ont",
      "label": "on / ont",
      "categoryName": "Confusion de mots",
      "fiche": { "titre": "on / ont", "astuce": "Remplacez par « avaient »…" },
      "correctUses": 2,
      "state": "travaillee",
      "stateSince": 1795000000000,
      "occurrences": 9,
      "firstFaultAt": 1794000000000,
      "lastFaultAt": 1795000000000,
      "tipsShown": 1,
      "choicesShown": 2,
      "choicesCorrect": 1,
      "choicesWrong": 1,
      "lastSolicitedAt": 1795000000000,
      "solicitationsThatDay": 1,
      "acquiredAt": null,
      "relapses": 0
    }
  ],
  "counts": { "observee": 4, "signalee": 1, "travaillee": 1, "acquise": 0 },
  "thresholds": { "signalementOccurrences": 3, "signalementFenetreJours": 7, "…": "…" }
}
```

| Champ | Sens |
|---|---|
| `state` | `observee`, `signalee`, `travaillee` ou `acquise` |
| `stateSince` | date d'entrée dans l'état courant |
| `label`, `fiche` | nom lisible de la règle ; `fiche` vaut `null` pour une règle sans fiche |
| `occurrences` | nombre total de fautes sur la règle |
| `tipsShown` | astuces affichées depuis la dernière entrée en « signalée » |
| `choicesShown`, `choicesCorrect`, `choicesWrong` | choix à deux formes proposés, bonnes et mauvaises réponses |
| `acquiredAt` | date d'acquisition ; `null` si la règle n'est pas acquise |
| `relapses` | nombre de rechutes (faute après acquisition) |
| `thresholds` | les seuils en vigueur |

### `GET /api/rules/events?limit=200&ruleKey=…`

Historique daté, du plus récent au plus ancien. `limit` va de 1 à 1000 (200 par défaut) ; `ruleKey` restreint à une règle.

```json
{
  "events": [
    { "id": 12, "ruleKey": "PAIRE:on/ont", "at": 1796300000000, "type": "rechute", "from": "acquise", "to": "signalee" },
    { "id": 11, "ruleKey": "PAIRE:on/ont", "at": 1796200000000, "type": "acquise", "from": "travaillee", "to": "acquise" },
    { "id": 10, "ruleKey": "PAIRE:on/ont", "at": 1795000000000, "type": "reponse_juste", "from": null, "to": null }
  ]
}
```

`type` vaut `observee`, `signalee`, `travaillee`, `acquise` ou `rechute` pour un changement d'état (`from` et `to` sont alors renseignés ; `from` est `null` à la première faute), et `astuce`, `choix`, `reponse_juste` ou `reponse_fausse` pour une sollicitation. Il vaut `emploi` quand une règle suivie a été employée correctement dans un texte (confusions de mots seulement) : l'événement ne porte que la règle et la date.

### `POST /api/rules/answer`

Enregistre la forme cliquée lors d'un choix à deux formes. `choiceId` est celui reçu dans l'intervention. L'interface appelle cette route après avoir copié le texte ; un échec n'empêche pas la copie.

```json
{ "choiceId": 57, "correct": true }
```

Réponse : `{"recorded": true, "nouveauxBadges": []}`. Chaque choix ne reçoit qu'une réponse. `nouveauxBadges` a la même forme que dans `POST /api/analyze` (par exemple « Dix bons choix »).

| Code | Cas |
|---|---|
| 400 | corps invalide (`choiceId` entier, `correct` booléen) |
| 404 | aucun choix ne porte cet identifiant |
| 409 | le choix a déjà reçu sa réponse, ou un choix plus récent l'a remplacé pour la même règle |

### `GET /api/journal?days=7`

Bilan de la période (entier de 1 à 365 jours ; 7 si `days` est absent ou illisible, 1 pour une valeur inférieure à 1) : `period` (textes, mots, fautes, note), `unclassified`, et les vingt règles les plus fréquentes (`rules` : `ruleKey`, `label`, `categoryName`, `count`). `label` est le nom fixe de la règle : titre de sa fiche, description de la règle du moteur, ou à défaut sa catégorie ; jamais un extrait de vos textes.

### `GET /api/progress`

Tout l'écran **Progression** en une seule requête, calculé depuis le journal par `src/analysis/progression/calcul.ts` (réglages dans `reglages.ts`). Les semaines vont du lundi 0 h au lundi suivant, heure locale du serveur ; la dernière est la semaine en cours. L'état des règles est celui qui est enregistré : « acquise » n'est réévalué qu'à un `POST /api/analyze`. Mêmes contrôles que les autres routes du journal (en-tête `Host` et origine en mode bureau, CORS) ; 405 pour une autre méthode que `GET` ou `OPTIONS`.

Réponse (extrait, deux semaines sur douze) :

    ],

      { "ruleKey": "PAIRE:on/ont", "label": "on / ont", "categoryName": "Confusion de mots", "state": "acquise", "stateSince": 1792600000000, "occurrences": 11, "lastFaultAt": 1791300000000, "acquiredAt": 1792600000000 }

| Champ | Sens |
|---|---|
| `empty` | `true` quand le journal ne contient aucun texte |
| `since` | début de la première des `weeks` semaines affichées |
| `mastery.score` | score de maîtrise de 0 à 100 ; `null` tant que la fenêtre récente compte moins de `minimum.texts` textes ou `minimum.words` mots |
| `mastery.quality` | note moyenne des `recentWeeks` dernières semaines, ramenée sur 100 |
| `mastery.rulesShare` | part (sur 100) des règles acquises parmi les règles entrées dans le cycle (`inCycle` : signalées, travaillées, acquises) ; `null` s'il n'y en a aucune, le score vaut alors la qualité seule |
| `totals`, `period`, `recent`, `previous` | depuis le premier texte, sur les semaines affichées, sur les `recentWeeks` dernières semaines, et sur les semaines d'avant de même durée |
| `faultsPer100`, `score` | fautes pour 100 mots et note sur 20 ; `null` sans aucun mot |
| `trend` | `baisse`, `hausse` ou `stable` pour les fautes pour 100 mots (`recent` contre `previous`) ; `null` si l'une des périodes n'a aucun mot |
| `series` | une entrée par semaine, de la plus ancienne à la plus récente |
| `rules.active`, `rules.acquired` | règles signalées ou travaillées (les plus récemment fautives d'abord), et règles acquises (les plus récemment acquises d'abord) |
| `frequentRules` | les huit règles les plus fréquentes sur les semaines affichées ; les fautes de frappe (`FR_SPELLING_RULE`) y figurent sous le libellé « Fautes de frappe » ; `state` vaut `null` pour une règle hors cycle |

Score : `arrondi(100 × (0,6 × qualité + 0,4 × part des règles acquises))`, qualité et part étant comprises entre 0 et 1 avant arrondi (qualité = note récente / 20). Sans règle entrée dans le cycle : `arrondi(100 × qualité)`. Explication en langage simple dans [Progression](/docs/utiliser/progression/).

#### `mesure` : ce que changent les astuces

La réponse porte aussi `mesure`, calculée par `src/analysis/progression/mesure.ts` (réglages `MESURE` dans `reglages.ts`) : pour chaque règle qui a reçu une intervention, le taux de fautes avant et depuis la première astuce, et le même calcul pour un groupe de comparaison. Explication en langage simple dans [Progression](/docs/utiliser/progression/#ce-que-changent-les-astuces).

```json
"mesure": {
  "motsParTaux": 1000,
  "minimum": { "avant": { "textes": 3, "mots": 400 }, "depuis": { "textes": 5, "mots": 1000 } },
  "premierTexte": 1788739200000,
  "suivies": [
    {
      "ruleKey": "PAIRE:on/ont", "label": "on / ont", "categoryId": "CONFUSION",
      "groupe": "suivie", "etat": "acquise", "pivot": 1788912000000,
      "avant": { "textes": 3, "mots": 427, "fautes": 3, "taux": 7 },
      "depuis": { "textes": 13, "mots": 2002, "fautes": 1, "taux": 0.5 },
      "suffisant": true, "avantTropCourt": false, "textesManquants": 0, "evolution": -93,
      "astuces": 1, "choix": 0, "reponsesJustes": 0, "reponsesFausses": 0,
      "rechutes": 0, "acquiseLe": 1790035200000
    }
  ],
  "comparaison": [
    { "ruleKey": "FR_SPELLING_RULE", "label": "Fautes de frappe", "groupe": "comparaison", "etat": null, "…": "…" }
  ],
  "synthese": {
    "suivies": { "regles": 3, "reglesSuffisantes": 3, "avant": { "textes": 16, "mots": 2363, "fautes": 10, "taux": 4.2 }, "depuis": { "textes": 32, "mots": 4924, "fautes": 4, "taux": 0.8 }, "evolution": -81 },
    "comparaison": { "regles": 1, "reglesSuffisantes": 1, "…": "…" }
  },
  "choix": { "justes": 3, "fausses": 1, "taux": 75 },
  "acquises": { "total": 1, "restees": 1, "rechutes": 0 }
}
```

| Champ | Sens |
|---|---|
| `suivies` | règles qui ont reçu au moins une intervention ; `pivot` : date de la première astuce (ou du premier choix à deux formes, s'il n'y a jamais eu d'astuce) |
| `comparaison` | fautes comptées qui ne reçoivent jamais d'intervention (`REGLES_HORS_CYCLE` : `FR_SPELLING_RULE`) ; `pivot` : date à laquelle elles remplissent le même critère de signalement (3 fautes en 7 jours) |
| `avant` | fautes de la règle jusqu'au pivot compris, sur les textes écrits entre sa première faute et le pivot |
| `depuis` | fautes et textes après le pivot |
| `taux` | fautes pour `motsParTaux` (1 000) mots, arrondi au dixième ; `null` sans aucun mot |
| `suffisant` | les deux périodes atteignent `minimum` ; sinon `avantTropCourt` (période avant trop courte, elle ne s'allongera plus) ou `textesManquants` (textes à écrire encore, estimés sur la longueur moyenne des textes) |
| `evolution` | évolution relative du taux, en % entier (négatif : baisse), calculée sur les nombres exacts ; `null` si la règle n'est pas `suffisant` |
| `synthese` | par groupe, somme des fautes sur somme des mots des seules règles `suffisant` (pas une moyenne de taux) ; un même texte compte pour chaque règle mesurée |
| `choix` | réponses aux choix à deux formes (justes, fausses) et part de bonnes réponses en % |
| `acquises` | règles acquises au moins une fois, celles qui n'ont jamais rechuté depuis, et le nombre de rechutes |

`label` sert à l'écran et n'est jamais exporté. Aucun test statistique n'est fait : seulement des chiffres et leurs volumes.

### `GET /api/progress/export`

Export anonyme de la bêta, au format `grammaria-beta` version 1 (`src/analysis/progression/export.ts`). La route ne fait que renvoyer le JSON : rien n'est envoyé nulle part, l'interface en fait un fichier (téléchargement du navigateur, ou commande Rust `export_beta_enregistrer` sur le bureau, qui l'écrit dans le dossier Téléchargements sous le nom `grammaria-beta-<8 premiers caractères du participant>.json`). Le premier appel crée l'identifiant aléatoire du participant (128 bits, table `beta_participant`), gardé jusqu'à l'[effacement du journal](#delete-apijournal). L'export est validé (`validerExport`) avant de sortir. Mêmes contrôles que les autres routes du journal ; 405 pour une autre méthode que `GET` ou `OPTIONS`.

Le format ne contient que des nombres entiers positifs, des booléens et des chaînes de forme contrôlée, et rien d'autre :

| Champ | Forme |
|---|---|
| `format`, `version` | `"grammaria-beta"`, `1` |
| `application` | version de Grammaria, `x.y.z` |
| `plateforme` | `"bureau"` ou `"serveur"` |
| `participant` | 32 caractères hexadécimaux, tirés au hasard ; ne dérive d'aucune donnée de la machine ni de l'utilisateur |
| `seuils` | `SEUILS` (cycle de vie des règles) et `MESURE` en vigueur : deux exports ne se comparent qu'avec les mêmes |
| `semaines` | une entrée par semaine relative, sans trou, de 0 (semaine du premier texte corrigé) à la semaine de l'export ; une semaine est un bloc de 7 × 24 heures, sans calendrier ni fuseau. Aucune date ni heure absolue n'est exportée |
| `regles[].regle` | identifiant de règle du moteur (`[A-Z0-9_]+`) ou d'une fiche maison, prise dans sa liste fermée (`PAIRE:a/à`, `TERMINAISON:er/é`…). Une règle d'une autre forme n'est pas exportée. Aucun libellé |
| `regles[].categorie` | identifiant de catégorie du moteur (`[A-Z0-9_]*`) |
| `regles[].groupe`, `etat` | `suivie` ou `comparaison` ; état du cycle (`observee`, `signalee`, `travaillee`, `acquise`), `null` pour la comparaison |
| `regles[].semainePivot`, `semaineAcquisition` | semaines relatives (`null` : jamais acquise) |
| `regles[].avant`, `depuis`, `suffisant` | volumes de la [mesure](#mesure--ce-que-changent-les-astuces) ; les taux s'en déduisent |
| `synthese` | les totaux de la mesure |

`validerExport` refuse tout champ inconnu ou manquant, tout type inattendu, toute chaîne hors de ces formes, tout nombre négatif, non entier, non fini ou supérieur à un milliard, plus de 520 semaines ou de 1 000 règles, et un fichier de plus de 2 Mo. Ses messages d'erreur ne citent jamais le contenu refusé. La collecte des fichiers se fait avec `npm run beta:agreger` (voir [Développement](/docs/reference/developpement/#bêta--collecte-des-exports)).

### `DELETE /api/journal`

Efface tout le journal, remet à zéro l'état des règles et leur historique, et efface les badges obtenus. Réponse : `{"purged": true}`.

## Badges

Le catalogue est défini dans `src/analysis/badges/catalogue.ts`, l'évaluation dans `src/analysis/badges/evaluation.ts` (logique pure). Les badges sont réévalués après chaque `POST /api/analyze` et chaque réponse enregistrée par `POST /api/rules/answer`. Un badge obtenu est conservé avec sa date dans la table `badges` du journal et n'est jamais retiré par un recalcul ; seul `DELETE /api/journal` l'efface. Liste et critères : [Badges](/docs/utiliser/badges/).

### `GET /api/badges`

Catalogue complet, dans l'ordre d'affichage : chaque badge, obtenu ou non, avec sa progression.

```json
{
  "familles": [{ "id": "premiers-pas", "titre": "Premiers pas" }, { "id": "regularite", "titre": "Régularité" }, "…"],
  "badges": [
    {
      "id": "premier-texte",
      "famille": "premiers-pas",
      "titre": "Premier texte",
      "description": "Votre premier texte est corrigé : le journal de progression commence.",
      "critere": "Corriger un premier texte.",
      "mesure": "textes",
      "unite": { "singulier": "texte", "pluriel": "textes" },
      "obtenu": true,
      "obtenuLe": 1795000000000,
      "progression": { "valeur": 7, "seuil": 1 }
    },
    {
      "id": "note-18",
      "famille": "justesse",
      "titre": "Plume sûre",
      "…": "…",
      "obtenu": false,
      "obtenuLe": null,
      "progression": {
        "valeur": 16.4,
        "seuil": 18,
        "detail": "7 textes corrigés sur les 30 derniers jours (10 au minimum)."
      }
    }
  ],
  "obtenus": 3,
  "total": 18
}
```

| Champ | Sens |
|---|---|
| `id` | identifiant stable du badge |
| `famille` | `premiers-pas`, `regularite`, `justesse`, `maitrise` ou `perseverance` |
| `critere` | critère en clair, affiché tant que le badge est à venir |
| `mesure` | ce qui est compté : `textes`, `jours`, `semaines`, `textesSansFaute`, `noteMoyenne`, `reglesAcquises`, `homophonesAcquis`, `rechutesSurmontees` ou `reponsesJustes` |
| `obtenuLe` | date d'obtention (date du fait qui a rempli le critère) ; `null` si le badge est à venir |
| `progression.valeur` | valeur actuelle de la mesure ; pour `noteMoyenne`, note moyenne des 30 derniers jours (0 sans texte) |
| `progression.seuil` | valeur à atteindre ; pour `noteMoyenne`, une note sur 20 |
| `progression.detail` | précision éventuelle, en clair |

Cette route est soumise aux mêmes contrôles que les autres routes du journal (en mode bureau : en-tête `Host` local obligatoire). 405 pour une autre méthode que `GET`.

## Mots valides

`GET` et `POST /api/valid-words` lisent et complètent `public/data/valid-words.json`. Ces routes sont héritées d'ai_corrector ; l'interface actuelle ne les utilise pas.
